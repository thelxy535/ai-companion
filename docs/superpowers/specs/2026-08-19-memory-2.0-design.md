# CC-Switch Memory 2.0 设计规范

## 目标

将现有的消息历史、基础记忆和向量记忆升级为完整的本地优先记忆系统。系统必须可审计、可恢复、可解释，并支持多个伴侣/角色之间严格隔离。AI 只能产生候选和整理提案，不能绕过用户审核直接修改正式记忆。

## 核心不变量

1. 原始消息和事件是不可覆盖的来源记录。
2. 候选记忆与正式记忆分离；候选默认处于 `pending`。
3. 用户编辑产生新版本，旧版本保留且可恢复。
4. 新旧冲突并存，进入审核，不自动覆盖。
5. 每条记忆必须绑定角色范围（伴侣、会话或共享范围），禁止跨角色污染。
6. 删除使用软删除，可恢复；导出包含来源、版本和审核结果。
7. 所有自动操作写入审计记录，失败不得破坏已有记忆。

## 数据模型

### 现有兼容边界

当前 Room 数据库版本为 `10`。现有核心表包括 `messages`、`memories`、`user_profiles`、`mood_states`、`vector_memories`、`tags`、`message_tags`、`interaction_times`、`user_events` 和 `custom_characters`。Memory 2.0 只新增表和正向迁移，不删除或重写这些表；旧数据通过内容哈希桥接到来源和正式记忆，原有聊天读取路径保持不变。

### MemorySource

原始来源记录，关联 `MessageEntity` 或导入事件。字段至少包括 `id`、`scopeKey`、`messageId`、`contentSnapshot`、`sourceType`、`occurredAt`、`contentHash`、`createdAt`。来源记录不可变。

### MemoryReview

AI 或用户创建的候选。字段包括 `id`、`scopeKey`、`kind`、`title`、`content`、`confidence`、`status`（`pending/accepted/rejected/deferred/conflict`）、`sourceIds`、`proposalHash`、`createdAt`、`resolvedAt` 和 `resolutionNote`。接受候选时生成正式记忆，不直接把候选改写成正式记忆。

### MemoryNode

正式记忆。字段包括 `id`、`scopeKey`、`kind`、`subjectRole`、`subjectKey`、`title`、`content`、`importance`、`confidence`、`validFrom`、`validUntil`、`status`（`active/expired/revoked/deleted`）、`createdAt`、`updatedAt` 和 `currentVersion`。

记忆类型首批支持：`identity`、`preference`、`habit`、`goal`、`event`、`relationship`、`emotion`、`capability`、`value`、`observation`。

### MemoryEvidence

记忆与来源的关联，保存 `sourceId`、证据角色（支持/反驳/上下文）、可信度、摘要快照和创建时间。删除来源不会静默删除证据，而是标记为不可用。

### MemoryVersion

每次创建、编辑、合并、拆分和恢复都会生成版本，保存完整内容快照、变更原因、操作者（用户/模型/系统）、审核引用和时间戳。

### MemoryRelation

有向关系边，连接两个记忆节点，包含关系类型（支持、冲突、因果、属于、相关）、权重、证据引用、状态和版本。关系提案必须先审核才能生效。

### RetrievalTrace / RetrievalFeedback

记录一次召回的查询范围、候选节点、排序原因、实际注入内容和耗时。用户可对召回标记有用、无关、错误或禁用；反馈只追加记录，不覆盖历史轨迹。

## 数据流

```text
消息/导入事件
  -> 不可变来源记录
  -> 候选提取与去重
  -> 审核中心
  -> 正式记忆与证据
  -> 关系/冲突提案
  -> 召回与反馈
  -> 后续整理提案
```

自动提取、合并、压缩、过期判断和关系发现都必须产出提案。模型失败、解析失败或数据库写入失败时，保留来源记录并显示可重试状态。

## 召回策略

召回先按 `scopeKey` 和记忆状态过滤，再综合关键词、向量相似度、重要性、置信度、时间衰减、最近反馈和冲突状态排序。冲突或被用户标记错误的节点默认不注入对话，但仍可在记忆库中查看和解决。每次召回都写入轨迹，便于解释“为什么记住/用了什么”。

## 用户界面

记忆入口分为四个互相联动的视图：

- **记忆脑图**：查看主题、事件、人物和关系；点击节点打开详情。
- **记忆库**：按类型、角色、状态、时间、重要性和搜索词筛选；支持批量操作。
- **审核中心**：候选、冲突、关系提案和过期建议分组处理；支持接受、编辑、拒绝、延后、合并、拆分。
- **记忆详情**：显示当前版本、历史版本、来源证据、关系、召回记录和隐私操作。

界面必须明确区分“来源”“候选”“正式记忆”，并在任何自动生成内容旁标出状态和证据数量。

## 迁移与兼容

保留现有 `memories`、`messages` 和向量表，新增表通过 Room migration 建立。现有记忆迁移为 `MemorySource + MemoryNode`，来源可信度标记为 `legacy`，不自动伪造审核记录。导入支持旧格式并生成 `importRun`，重复导入依据内容哈希幂等处理。导出包含 schema 版本，允许在失败时回滚本次导入而不影响已有数据。

## 隐私与可靠性

支持按角色禁用记忆、单条记忆禁用召回、敏感内容标记、软删除和恢复。数据库操作使用事务；跨表写入失败整体回滚。所有后台任务可取消、可重试，并限制单次处理数量以避免阻塞 UI。

## 分阶段交付

1. 核心表、枚举、migration、来源/候选/正式记忆仓库和测试。
2. 审核中心、记忆库、详情页及版本/证据操作。
3. 冲突与关系提案、角色隔离和基础召回轨迹。
4. 脑图与时间线、向量召回融合、反馈闭环。
5. 自动整理、迁移工具、性能优化、隐私控制和真机验收。

每阶段都保持旧消息历史和现有聊天流程可用；任何阶段失败都不能丢失来源记录或已确认记忆。

## 验收标准

- AI 生成候选后，未审核内容不会进入正式记忆或对话召回。
- 接受、编辑、合并、拆分、撤销和恢复均可查看完整历史。
- 不同角色的记忆查询和召回互不泄漏。
- 任意正式记忆可定位到来源证据，并能解释召回原因。
- 旧数据库和旧导出可迁移；重复导入不产生重复节点。
- Room 单元测试、迁移测试、ViewModel 测试和关键 UI 流程测试通过。
- 在 Android 设备上离线可浏览、审核和恢复记忆；后台整理失败可重试。
